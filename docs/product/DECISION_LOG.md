## ADR-001: PostgreSQL GiST Exclusion Constraints for Authoritative Concurrency

### Context
In a time-slotted parking marketplace, double-bookings occur when two concurrent checkout requests attempt to reserve the same physical bay for overlapping time intervals. Initial drafts proposed managing holds via Redis keys (`hold:{space_id}`). However, coarse-grained space locking blocks non-overlapping bookings (e.g., 10:00-11:00 blocks 14:00-15:00), and relying solely on application-layer distributed locks creates split-brain risks during network partitions or Redis restarts.

### Decision
We will enforce temporal exclusion directly inside PostgreSQL using the `btree_gist` extension, range types (`tstzrange`), and a database-level exclusion constraint:
```sql
CONSTRAINT prevent_overlapping_active_reservations
EXCLUDE USING gist (
    parking_space_id WITH =,
    time_window WITH &&
) WHERE (status IN ('ACTIVE_HOLD', 'CONFIRMED', 'ACTIVE_SESSION', 'MAINTENANCE_BLOCK', 'OWNER_BLACKOUT'));
```
PostgreSQL is the single authoritative source of truth. Redis is used solely for non-authoritative caching, rate-limiting, and countdown presentation.

### Consequences
- **Positive:** Mathematically eliminates race conditions and double-bookings. Concurrency is guaranteed by the database engine ACID transaction serializer.
- **Negative:** GiST index writes are slightly more CPU-intensive than standard B-Trees. Requires `btree_gist` extension enabled in RDS.

## ADR-002: In-Process Modular Monolith on Python FastAPI over Microservices

### Context
Microservice architectures introduce substantial operational overhead: distributed transactions, eventual consistency latencies, complex API gateways, and multi-repo deployment overhead. For an early-stage parking marketplace, booking and payment confirmation must execute atomically within sub-millisecond database transactions.

### Decision
We will build SmartPark as an in-process **Modular Monolith** using **Python FastAPI**. Domains (Auth, Inventory, Bookings, Payments, Ledger, Access) are encapsulated within separate Python packages communicating via typed in-memory service contracts. Cross-domain database mutations execute within single ACID transactions.

### Consequences
- **Positive:** Zero distributed transaction lag; rapid developer iteration; single Docker container deployment on AWS ECS Fargate; trivial local testing.
- **Negative:** Requires strict discipline to prevent spaghetti imports across domain packages.

## ADR-003: Architectural Separation of Payment QR and Parking Access QR Subsystems

### Context
Earlier conceptual drafts loosely referred to "the QR code" for both payment and physical entry, creating severe security risks. Conflating payment tokens with gate passes allows drivers to reuse payment receipts as gate passes or exposes payment transaction IDs to security guards.

### Decision
We enforce an absolute architectural wall between the two systems:
1. **Payment Dynamic QR:** Generated by Razorpay, encodes NPCI UPI transaction string, 480-second (8-minute) TTL, scanned by driver UPI app to transfer funds.
2. **Parking Access QR:** Generated by SmartPark server, encodes an unguessable 128-bit opaque token (`spx_...`), valid during booking window, scanned by Guard app via `mobile_scanner`, atomically burned upon entry.

### Consequences
- **Positive:** Zero PII leakage in access QR; single-use replay protection; guard app has zero access to payment credentials.
- **Negative:** Requires rendering two distinct QR flows in the Flutter client.

## ADR-004: Append-Only Double-Entry Financial General Ledger Architecture

### Context
Using a loose `amount_paid` column on a booking table fails standard financial audits, makes partial refund reconciliation error-prone, and violates Indian regulatory accounting standards. Furthermore, using the word "escrow" without an RBI escrow license creates legal liability.

### Decision
We implement a true **Double-Entry General Ledger** (`ledger_entries`) with a standard Chart of Accounts (1010 Gateway Transit, 2010 Owner Payable, 2030 GST Payable, 3010 Commission, etc.). Every posted transaction satisfies $\sum \text{Debits} = \sum \text{Credits}$. Posted rows are immutable (`REVOKE UPDATE, DELETE`). Refunds and reversals execute via new balancing journal entries.

### Consequences
- **Positive:** Complete mathematical auditability; trivial tax reconciliation; compliant with RBI payment intermediary guidelines; zero unbacked "escrow" claims.
- **Negative:** Requires writing balanced multi-line journal entries for every transaction, increasing database insert volume.

## ADR-005: Two-Phased Marketplace Payout Strategy (Direct Bank Payout Fallback)

### Context
Automated marketplace split products like Razorpay Route require participating merchants to have an annual domestic turnover exceeding ₹40 Lakhs per RBI guidelines. A Day 1 startup cannot meet this threshold before launch.

### Decision
We adopt a **Two-Phased Settlement Architecture**:
- **Phase 1 (Day 1 Pilot):** Merchant of Record Batch Bank Payouts via RazorpayX Payouts or Cashfree Payouts API (IMPS/NEFT) executing weekly batch settlements against verified bank accounts from the corporate current account under prior bank agreement. The database ledger schema is 100% identical.
- **Phase 2 (Scale >₹40L Turnover):** Migrate seamlessly to Razorpay Route linked account transfers without any database schema migration.

### Consequences
- **Positive:** Allows immediate commercial launch without waiting for ₹40L turnover qualification while maintaining automated, auditable payouts.
- **Negative:** Phase 1 requires maintaining an operational disbursement account with RazorpayX.

## ADR-006: Firebase Phone Auth Client SDK with Authoritative Server JWT Minting

### Context
Indian urban drivers demand passwordless mobile phone login. Managing private SMS gateways, telecom DLT registration, and OTP cryptography in-house for MVP introduces heavy operational burden and SMS infrastructure costs.

### Decision
We adopt **Firebase Phone Authentication** on Flutter for native handset OTP auto-retrieval and Play Integrity device verification. However, the client-side Firebase token is **strictly untrusted** for business APIs. The Flutter app exchanges the Firebase ID token with the FastAPI backend, which verifies the cryptographic signature via the Firebase Admin Python SDK and mints an internal scoped SmartPark JWT.

### Consequences
- **Positive:** Free tier covers 10,000 monthly active users; battle-tested telecom SMS routing; high delivery rates across Indian carriers (Jio, Airtel).
- **Negative:** Verification costs scale at ~$0.015/SMS beyond 10,000 MAU, requiring migration planning at scale.

## ADR-007: Single Cross-Platform Flutter Mobile Binary with Dynamic Role Navigation

### Context
SmartPark serves four personas: Drivers, Space Owners, Gate Guards, and Operations Staff. Building 4 separate mobile applications would quadruple CI/CD maintenance, code duplication, and app store review overhead.

### Decision
We will build a **single cross-platform Flutter application** deploying to Android and iOS. The app dynamically renders role-specific shells (`DriverTabs`, `OwnerTabs`, `GuardTabs`, `OpsView`) based on verified JWT role claims. Multi-role users (e.g., Driver + Owner) switch viewports seamlessly via a profile toggle without re-authenticating.

### Consequences
- **Positive:** 100% shared networking, caching, and state management code; single binary to publish on Google Play Store and Apple App Store.
- **Negative:** Binary size is slightly larger (~25MB); requires strict route guard authorization to prevent UI cross-role leaks.

## 8. ADR-008: Controlled Manual Fallback Protocol for Offline Guard Operations

### Context
Gate entrances are frequently located in deep underground basements where mobile cellular reception is non-existent. Claiming "offline one-time cryptographic QR burning" without hardware synchronization between disconnected devices is mathematically impossible and vulnerable to replay attacks.

### Decision
Authoritative one-time QR consumption requires online connection. In offline basement environments, the Guard app switches to a **Controlled Manual Fallback Mode**: the guard cross-checks the physical vehicle license plate against a locally cached 8-hour shift schedule, confirms entry manually, logs an offline entry record, and syncs reconciliation once connectivity is restored.

### Consequences
- **Positive:** Honest, operationally realistic, and resilient to cellular dead zones without making unprovable cryptographic claims.
- **Negative:** Introduces minor manual overhead for guards in deep basements.

## 9. ADR-009: Late Payment Resolution Protocol (LPRP) with Automated Full Refund

### Context
A driver's 480-second (8-minute) checkout hold can expire right as they enter their UPI PIN. Another driver might immediately claim the bay, followed seconds later by the arrival of the first driver's captured payment webhook. The system must never create a double-booking.

### Decision
When a `payment.captured` webhook arrives for an expired hold:
1. Backend attempts to atomically transition the reservation to `CONFIRMED`.
2. If the slot has been claimed by another driver, PostgreSQL throws an `ExclusionViolation`.
3. The system catches the error, marks the reservation `RELEASED_UNFULFILLABLE`, and **automatically initiates an asynchronous 100% full refund** via Razorpay Refund API (`REFUND_ELIGIBLE` $\to$ `REFUND_REQUESTED` $\to$ `GATEWAY_ACCEPTED`) with reason `HOLD_EXPIRED_SLOT_UNAVAILABLE`.
4. Driver receives an immediate push notification with refund tracking reference. Banking rail settlement completes in 5-7 business days. Zero double-bookings occur.

### Consequences
- **Positive:** Absolute protection against double-booking; transparent, automated customer refund workflow without manual customer support tickets.
- **Negative:** Platform absorbs minor gateway processing fee (~₹2.17) on lost race conditions.

## 10. ADR-010: Pessimistic Conflict Resolution in Multi-Source Availability Intelligence (MSAI)

### Context
Different operational signals frequently conflict: an owner's calendar might show a bay available, but a security guard may have reported an unauthorized car parked in the bay 10 minutes prior.

### Decision
MSAI adopts **Strict Pessimistic Safety**: when any reliable evidence source indicates obstruction, maintenance, or conflict, the bay's state is forced to `UNCERTAIN` or `BLOCKED`. A bay is presented as `AVAILABLE` if and only if **all** validation checks pass cleanly. Missing or stale evidence is never treated as positive availability.

### Consequences
- **Positive:** Protects the brand promise; prevents drivers from arriving at obstructed spaces.
- **Negative:** Slightly reduces theoretical inventory availability in favor of 100% fulfillment dependability.
